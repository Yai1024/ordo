## 决策 1 · 四层单向依赖架构

### 背景

作业明确要求"菜单交互、数据处理与核心算法分开"。若不预先切分，一年内必然退化成
"一个 `main.cpp` 装全部逻辑"，届时无法测试、无法替换算法、无法复用。

### 决定

分为 `cli → app → {algo, io}` 四层，依赖严格单向，接口在 `include/ordo/` 中声明：

| 层 | 目录 | 职责 | 禁止 |
| --- | --- | --- | --- |
| L1 | `cli/` | 参数解析、菜单、打印 | 任何文件 I/O、任何算法实现 |
| L2 | `app/` | 编排一次业务动作 | 解析命令行、实现算法 |
| L3 | `algo/` | 纯函数计算 | I/O、取系统时钟、抛异常 |
| L4 | `io/` | 持久化 | 业务规则 |

### 后果

- **正面**：`algo/` 可脱离文件与菜单单测；换存储格式只改 `io/` 一个文件；
  作业答辩时"核心算法在哪"有唯一答案。
- **负面**：每个功能要写接口 + 实现两份；小改动要跨两三个文件。
  对一个千行级项目这是可接受的开销。
- **约束**：`main.cpp` 是唯一的依赖装配点。

### 备选方案

- 单文件 + 分区注释：作业最小化写法，但不可测试、不可演进。**否决**。
- MVC 三层（Model/View/Controller）：缺少"算法"这一独立轴的显式位置，
  而本题的技术分全在算法。**否决**。

## 决策 2 · 以 Makefile 为唯一构建入口，暂不引入 CMake

### 背景

本机实测：`g++ 16.2.0`（MinGW-w64）与 `GNU Make 4.4.1` 可用，**`cmake` 未安装**。
作业只要求"注明编译器或开发环境"，不要求跨平台构建系统。

### 决定

`Makefile` 为唯一构建入口，提供 `all / test / run / clean / fmt / fmt-check`。
源码文件名用 `$(wildcard)` 自动收集，新增 `.cpp` 无需改构建脚本。
CMake 不在本期引入。

### 后果

- **正面**：零安装即可编译；改文件不用动构建脚本；构建规则 30 行内可读完。
- **负面**：不跨平台（MSVC 用户无法直接用）；无增量编译（当前全量编译 < 5 秒，可接受）。
- **触发重审**：若源文件超过 40 个、全量编译超过 10 秒，或需要 MSVC 构建，再写 ADR-0002 引入 CMake。

### 备选方案

- 直接 `g++ *.cpp`：无测试目标、无清理，随文件增多会失控。**否决**。
- CMake：更正式，但本机不可用，装了也只是配置负担。**推迟**。

## 决策 3 · 跨层错误用 `Result<T>`，不用异常

### 背景

作业要求处理"空数据、输入错误、重复记录、文件不存在"四类情况。它们都**可预期**，
不是异常状态。若用异常，容易写出"调用处忘了 catch → 整个程序终止"的代码。

### 决定

- 跨层通信一律使用 `Result<T>` / `Status` + `ErrorCode`（见 `OUTLINE.md` §7.2）。
- 业务层不抛异常；`std::bad_alloc`、`std::filesystem_error` 等标准库异常
  只在穿越 `main()` 时统一捕获，转换为退出码。
- 错误消息（`Status::message`）为面向用户的中文，可被 CLI 直接打印。

### 后果

- **正面**：编译器强制处理失败分支；算法层接口天然变成"纯函数 + 结果码"，易于测试。
- **负面**：调用处代码变长（每个 `Result` 都要判）；`Result<T>` 需自研约 40 行。
- **约束**：不得出现 `Result<Result<T>>` 这类嵌套；失败即返回，不继续传递中间态。

### 备选方案

- 异常 + RAII：C++ 惯用法，但本题的错误都不是"异常"。**否决**。
- `std::optional<T>` + 全局错误码：丢失错误消息，无法区分"文件不存在"与"格式损坏"。**否决**。

## 决策 4 · 零第三方依赖（含测试框架）

### 背景

长期维护的最大杀手是依赖腐烂：包管理器换了、版本不兼容、链接库缺失。
本项目体量小，标准库足够。

### 决定

- 不使用 GTest / Catch2 / fmt / spdlog / nlohmann-json 等任何第三方库。
- 测试框架自研（`tests/test_framework.h`，约 40 行宏）。
- 序列化只用 CSV 与 INI 这类纯文本格式，自行解析。

### 后果

- **正面**：十年后仍可 `mingw32-make` 即编译；仓库体积小；答辩时可完整解释每一行。
- **负面**：需要自己写 CSV 转义、时间解析、断言宏；测试报告不如 GTest 漂亮。
- **触发重审**：仅当某功能的自研成本超过两周工作量时才考虑引入依赖，且必须写 ADR 论证。
