--------------------------------------------------------------------------------
1.1  一句话
--------------------------------------------------------------------------------

Ordo 是一个用 C++ 写的命令行小工具：你把"这周要做的任务"录进去，它告诉你
今晚先做哪件、做多久、哪件已经排不下了。

名字来自拉丁语 ordo（次序、编排）。中文名叫"学习任务编排器"。

--------------------------------------------------------------------------------
1.2  它到底解决什么问题（举一个具体例子）
--------------------------------------------------------------------------------

假设今晚 18:30 到 23:00 你有 270 分钟，手上有三件事：

  A. 高数作业     截止明天 08:00   预估 90 分钟   重要度 5
  B. 英语背单词   截止三天后       预估 30 分钟   重要度 3
  C. 实验报告     截止下周         预估 180 分钟  重要度 4

一个"待办清单"只能把这三条列出来，怎么排全靠你自己想。
Ordo 要做的是：

  1. 算紧急度：A 明天就交，最急；C 还早但有 180 分钟，排不下；
  2. 排顺序：A → B → C，并说明为什么；
  3. 装箱：把 270 分钟切成 90 + 30 + 150，C 还剩 30 分钟排不进去；
  4. 报冲突：明确告诉你"C 差 30 分钟，建议今晚少睡半小时或改到明晚"。

第 4 步是关键：排不下不是错误，是必须能被解释的结果。

1.4  五分钟跑起来
--------------------------------------------------------------------------------

打开终端（Git Bash 或 PowerShell 都行），进入项目根目录，依次执行：

  命令 1:  mingw32-make
  会发生:  调用 g++ 编译 src/main.cpp，生成 bin/ordo.exe
  成功标志: 屏幕上出现 "==> built: bin/ordo"

  命令 2:  ./bin/ordo --version
  会发生:  运行程序，打印 "ordo 0.1.0"
  说明:    --version 是命令行参数，程序识别到它就直接打印版本然后退出

  命令 3:  ./bin/ordo
  会发生:  打印 "ordo 0.1.0 - skeleton build (M0)"
  说明:    不带参数时，M0 阶段只提示骨架就绪；M1 之后这里会进入交互菜单

  命令 4:  mingw32-make test
  会发生:  编译测试程序，然后运行 1 个测试用例，全部通过
  成功标志: "1 case(s), 0 assertion failure(s)"

  命令 5:  mingw32-make clean
  会发生:  删除 bin/ 目录，把编译产物清干净

为什么要用 mingw32-make 而不是 make？
  本机安装的是 MinGW 工具链，它提供的命令名就叫 mingw32-make，没有 make。
  在 Linux / macOS 上把命令换成 make 就能用，Makefile 本身是通用的。

2.2  五层结构（这是"单元"的概念）
--------------------------------------------------------------------------------

代码不是一个 main 从头写到尾，而是分成五"层"（单元）。箭头表示"谁可以调用谁"：

   ┌────────────────────────────────────────────────────────┐
   │  cli/     命令层    读命令行参数 / 显示菜单 / 打印结果   │
   └───────────────────────────┬────────────────────────────┘
                               │ 只能往下调
   ┌───────────────────────────▼────────────────────────────┐
   │  app/     服务层    串起"取数据 → 算算法 → 存回去"      │
   └───────────┬───────────────────────────────┬────────────┘
               │                               │
   ┌───────────▼──────────────┐    ┌───────────▼────────────┐
   │  algo/   算法层（纯计算） │    │  io/     存储层（读写） │
   │  不碰文件、不碰时间       │    │  只认接口，实现可替换   │
   └──────────────────────────┘    └────────────────────────┘

为什么非要分这么细？三个理由：

  1. 能测试。算法层只接受"输入参数"、只返回"结果"，不读文件也不问系统时间，
     所以可以在没有数据文件的情况下单独测它算得对不对。
  2. 能替换。存储层藏在接口后面，将来从 CSV 换成 JSON，只改一个文件，
     上层一行都不用动。
  3. 能解释。答辩时被问"你的核心算法在哪"，答案是 algo/ 目录，不含糊。

铁律（违反任何一条都算设计错误，不是风格问题）：

  - cli/ 里不许出现 ifstream / ofstream（不许自己读写文件）
  - algo/ 里不许调用系统时钟（当前时间必须由调用方当参数传进来）
  - algo/ 里不许抛异常（失败用返回值表达）
  - io/ 的具体实现只在 src/main.cpp 里创建一次

--------------------------------------------------------------------------------
3.1  include/ordo/version.h    （8 行）
--------------------------------------------------------------------------------

【它是什么】
  版本号的唯一出处。程序里任何地方要用版本号，都包含这个文件，
  而不是到处手写 "0.1.0"。将来改版本只改这一处。

【逐行说明】

第 1 行   #pragma once
          头文件保护。同一个 .h 被多次 #include 时，编译器只处理第一次。
          老写法是 #ifndef/#define/#endif 三行，现在一行就够。

第 3 行   // Ordo 版本宏。与 CHANGELOG.md 保持一致，发布时同步修改。
          // 是单行注释，编译器完全忽略。

第 4 行   #define ORDO_VERSION_MAJOR 0
          定义"主版本号"宏，值是 0。宏是编译期的纯文本替换：
          代码里写 ORDO_VERSION_MAJOR，编译前就被换成 0。

第 5 行   #define ORDO_VERSION_MINOR 1
          次版本号，值是 1。项目做了向下兼容的新功能时 +1。

第 6 行   #define ORDO_VERSION_PATCH 0
          修订号，修 bug 时 +1。

第 8 行   #define ORDO_VERSION_STRING "0.1.0"
          给人看的完整版本字符串。注意值是带双引号的，它是一个字符串字面量。
          有了它，代码里可以写：
              std::cout << "ordo " ORDO_VERSION_STRING;
          两个字符串字面量挨在一起，C++ 会自动拼接成 "ordo 0.1.0"。

【一个坑】
  三个数字宏和这个字符串宏是分开维护的，改版本时必须一起改，否则会对不上。
  M1 可以考虑用一个宏自动拼出字符串，目前这样写更直白，适合新手阅读。

--------------------------------------------------------------------------------
3.2  src/main.cpp    （43 行）
--------------------------------------------------------------------------------

【它是什么】
  程序入口。整个程序从这里开始执行。
  它只做三件事：读命令行参数 → 决定干什么 → 返回退出码。
  M1 之后，这里还会多一个职责：装配所有对象（创建存储层、创建命令层）。

【逐行说明】

第 1-3 行   // 注释
            "本文件是唯一的依赖装配点"——意思是：只有这里允许 new 出具体的
            存储实现（比如 CsvTaskRepository），其他地方一律只认接口。

第 5 行     #include <iostream>
            引入标准输入输出流。有了它才能用 std::cout（屏幕输出）
            和 std::cerr（错误输出）。尖括号表示"标准库头文件"。

第 6 行     #include <string>
            引入 std::string。这里其实没直接用，但 print_usage 的参数链上
            会用到，属于"显式声明依赖"的写法。

第 7 行     #include <string_view>
            引入 std::string_view：一个"只读的字符串视图"，只存指针+长度，
            不拷贝字符，比 std::string 轻。适合只读不存的场景。

第 9 行     #include "ordo/version.h"
            引入自己的头文件。双引号表示"项目内的文件"，编译器会去 -Iinclude
            指定的 include 目录里找，所以路径写成 ordo/version.h。

第 11 行    namespace {
            匿名命名空间。里面的东西只在这个 .cpp 文件内可见，
            相当于 C 语言的 static，用来避免符号污染。

第 13 行    void print_usage(std::ostream& out) {
            定义一个打印用法的函数。参数是 std::ostream&（输出流的引用）：
              - 用引用而不是传值，因为流对象不能拷贝；
              - 传进来而不是直接用 std::cout，是为了让它既能打印到屏幕，
                也能打印到错误流 std::cerr。这就是"依赖注入"的最小例子。

第 14-19 行 out << "..." << ... << "...";
            std::ostream 重载了 << 运算符，连续 << 就是把内容依次写出去。
            \n 是换行符；\n\n 就是空一行。

第 20 行    }
            函数结束。

第 22 行    }  // namespace
            匿名命名空间结束。

第 24 行    int main(int argc, char** argv) {
            程序入口。返回值类型是 int，这个整数就是"退出码"：
              0 = 成功（约定俗成，操作系统和脚本靠它判断成败）
              非 0 = 失败（本程序用 2 表示"参数错误"）
            argc = 参数个数（含程序名自己）
            argv = 参数数组，argv[0] 是程序路径，argv[1] 起才是用户输入

第 25 行    for (int i = 1; i < argc; ++i) {
            从 1 开始遍历，跳过 argv[0]（程序自己的名字）。
            ++i 是前置自增，语义上比 i++ 更直接。

第 26 行    const std::string_view arg{argv[i]};
            把 C 风格字符串（char*）包成 string_view。
            const 表示这个视图指向的内容不会被我们修改。
            {argv[i]} 这种大括号初始化是 C++11 起的统一写法。

第 27 行    if (arg == "--version" || arg == "-v") {
            || 是"或"。只要用户给了 --version 或 -v 任一，就进入分支。

第 28 行    std::cout << "ordo " << ORDO_VERSION_STRING << '\n';
            打印版本。注意这里用 '\n'（单引号，一个字符）而不是 "\n"
            （双引号，字符串），两者都能换行，前者更轻。

第 29 行    return 0;
            正常结束，退出码 0。后面代码不再执行。

第 31-34 行 同样的套路处理 --help / -h：打印用法，返回 0。

第 35 行    std::cerr << "unknown option: " << arg << "\n";
            用户给了一个程序不认识的参数。cerr 是错误流，
            错误信息走 stderr 是命令行程序的通行做法（方便脚本单独捕获）。

第 36 行    print_usage(std::cerr);
            把用法也打到错误流，和上面的报错保持在同一处输出。

第 37 行    return 2;
            返回非 0，告诉调用这个程序的脚本"我失败了"。2 特指"用法错误"。

第 38 行    }
            循环结束。走到这里说明用户没给任何参数。

第 40 行    // M0：骨架就绪。M1 将在此装配 CsvTaskRepository 与 Dispatcher。
            注释，标记了 M1 的接入点。

第 41 行    std::cout << "ordo " << ORDO_VERSION_STRING << " - skeleton build (M0)\n";
            没参数时的默认输出。M1 之后这里会改成"启动交互菜单"。

第 42 行    return 0;
第 43 行    }
            正常结束。

【小结：这 43 行教了你什么】
  - 怎么读命令行参数、逐个判断
  - 怎么用退出码表达成功/失败
  - 为什么要把工具函数塞进匿名命名空间
  - 为什么参数要传 std::ostream& 而不是写死 std::cout

--------------------------------------------------------------------------------
3.3  tests/test_framework.h    （65 行）
--------------------------------------------------------------------------------

【它是什么】
  自研的极简测试框架，约 65 行，零第三方依赖。
  它让你可以这样写测试：

      ORDO_TEST(加法应该正确) {
          ORDO_CHECK_EQ(1 + 1, 2);
      }

  然后 make test 会自动找到这个用例并运行它。

【它解决的核心问题】
  怎么让"定义了测试用例"这件事自动被登记，不用手动一个个调用？
  答案是：利用 C++ 的"静态对象在 main 之前构造"这一特性。

【逐行说明】

第 1 行     #pragma once
            头文件保护，同上。

第 3-7 行   // 使用说明注释

第 9-13 行  #include 五个标准库头文件
            <cstdio>   提供 std::fprintf（格式化输出到 stderr）
            <sstream>  提供 std::ostringstream（把内容拼成字符串）
            <string>   提供 std::string
            <utility>  提供 std::move（把字符串"搬"进容器，避免拷贝）
            <vector>   提供 std::vector（动态数组）

第 15 行    namespace ordo::test {
            C++17 的嵌套命名空间写法，等价于 namespace ordo { namespace test { 。
            测试相关的东西放在 ordo::test 下，和业务代码隔开。

第 17-20 行 struct TestCase {
                std::string name;   // 用例名字，用于打印
                void (*fn)();       // 函数指针：指向"没有参数、没有返回值"的函数
            };
            一个 TestCase 就是"名字 + 一段可执行的代码"。

第 22-25 行 inline std::vector<TestCase>& registry() {
                static std::vector<TestCase> cases;
                return cases;
            }
            返回"用例登记表"。两个关键点：
              1. static 局部变量只在第一次执行到这里时构造一次，
                 之后一直存在，函数返回时也不会销毁。这是全局唯一的表。
              2. inline 允许这个函数在多个 .cpp 里各有一份定义而不冲突
                 （C++17 起 inline 变量/函数可以放在头文件里）。
            返回引用 &，所以外面拿到的是同一张表，不是副本。

第 27-30 行 inline int& failure_count() {
                static int failures = 0;
                return failures;
            }
            同上，返回"失败计数器"的引用。所有用例共享这一个计数器。

第 32-34 行 struct Registrar {
                Registrar(std::string name, void (*fn)()) {
                    registry().push_back({std::move(name), fn});
                }
            };
            登记员。构造函数一被调用，就把 (名字, 函数) 塞进登记表。
            它的用法在第 45 行的宏里——定义一个全局 Registrar 对象，
            程序启动时它的构造函数自动执行，用例就登记好了。
            这就是"零配置发现测试"的原理。

第 36-39 行 inline void report_failure(const char* file, int line,
                                            const std::string& what) {
                ++failure_count();                       // 失败数 +1
                std::fprintf(stderr, "  FAIL  %s:%d\n        %s\n",
                             file, line, what.c_str());
            }
            fprintf 是 C 语言的格式化输出：%s 占位字符串，%d 占位整数。
            what.c_str() 把 std::string 转成 C 风格字符串，因为 %s 要 char*。
            const std::string& 用引用传参，避免整个字符串被拷贝一遍。

第 41 行    }
            命名空间结束。

第 43-46 行 #define ORDO_TEST(case_name)                       \
                static void case_name();                       \
                static ::ordo::test::Registrar case_name##_registrar{#case_name, case_name}; \
                static void case_name()

            宏，把一行声明展开成三行：
              第 1 行：先声明一个函数（正式定义在用户写的大括号里）
              第 2 行：定义一个全局登记对象，名字 = 用例名 + "_registrar"
                       ## 是宏里的"拼接运算符"，case_name##_registrar
                       在 case_name 为 foo 时会变成 foo_registrar
                       ::ordo 前面的双冒号表示"从全局命名空间开始找"
              第 3 行：以 static void case_name() 开头，后面紧跟用户写的 { ... }

            所以用户写：
                ORDO_TEST(foo) { ORDO_CHECK(true); }
            展开后就是"函数声明 + 登记对象 + 函数定义"三合一。
            行尾的 \ 表示"这一行还没结束，下一行接着"。右边对齐的反斜杠只是好看。

第 48-53 行 #define ORDO_CHECK(cond) ...
                do {
                    if (!(cond)) {
                        ::ordo::test::report_failure(__FILE__, __LINE__, "assert: " #cond);
                    }
                } while (0)

            - __FILE__ / __LINE__ 是编译器内置宏，自动展开成当前文件名和行号。
            - #cond 是宏里的"字符串化运算符"，把参数原样变成字符串。
              所以失败时会打印 "assert: 1 + 1 == 3" 这样的原文。
            - 外面套 do { } while (0) 的原因：宏展开后如果不套循环，
              在 if 后面直接跟这个宏时会出现悬空 else 问题；
              包成一条语句就永远不会出错。这是 C/C++ 宏的标准防御写法。

第 55-65 行 #define ORDO_CHECK_EQ(actual, expected) ...
                do {
                    const auto& a_ = (actual);     // auto 自动推导类型
                    const auto& e_ = (expected);   // const& 避免拷贝
                    if (!(a_ == e_)) {
                        std::ostringstream os_;
                        os_ << #actual " == " #expected << "\n        actual  : " << a_
                            << "\n        expected: " << e_;
                        report_failure(__FILE__, __LINE__, os_.str());
                    }
                } while (0)

            比较两个值，不等就把"实际值"和"期望值"都打印出来，
            省得你再去猜到底差在哪。os_.str() 把拼好的内容取出成 std::string。
            a_ / e_ 加了尾随下划线，是为了避免和你传进来的变量重名。

【小结：这个 65 行文件教了你什么】
  - static 局部变量 = 函数内隐藏的全局变量
  - inline 让函数能安全地写在头文件里
  - 构造函数可以在 main 之前执行（全局对象初始化）
  - 宏里的 # 和 ## 分别做什么
  - do { } while (0) 为什么是宏的标准外壳

3.6  Makefile    （68 行）
--------------------------------------------------------------------------------

【它是什么】
  构建脚本。一行命令就能完成"编译全部源文件 → 生成可执行文件"。
  它同时是测试、清理、格式化的入口。

【整体结构】
  变量定义（1-24 行）→ 目标定义（26-68 行）
  Makefile 的语法是"目标: 依赖，然后换行 + TAB + 执行命令"。
  注意：命令前面必须是 TAB，不能是空格，这是 Make 最容易踩的坑。

【逐段说明】

第 1-4 行   # 注释：文件用途和用法

第 6-10 行  # Windows 下 mingw32-make 默认用 cmd.exe 执行命令，
            # mkdir -p / rm -rf 会失败。
            # 显式指定 POSIX shell（Git for Windows 自带 sh.exe）。
            ifeq ($(OS),Windows_NT)
            SHELL    := sh
            endif

            这一段是为了跨平台：Windows 的 cmd 不认识 mkdir -p 和 rm -rf，
            所以强制改用 sh 来执行命令。
            := 是"立即展开赋值"，?= 是"只在未定义时赋值"。

第 12 行    CXX      ?= g++
            编译器名字。如果环境里已有 CXX 变量，就用环境的，否则用 g++。

第 13 行    CXXFLAGS ?= -std=c++17 -Wall -Wextra -Wpedantic -Wshadow -Iinclude -O2 -g
            编译选项，逐个解释：
              -std=c++17   使用 C++17 标准
              -Wall        打开常见警告
              -Wextra     打开更多警告
              -Wpedantic  严格按标准检查
              -Wshadow    变量遮蔽同名变量时警告
              -Iinclude   头文件的搜索目录（所以能写 #include "ordo/version.h"）
              -O2         二级优化，让程序跑得快
              -g          保留调试信息，方便 gdb 调试

第 14 行    LDFLAGS  ?=
            链接选项，目前为空。

第 15 行    FORMAT   ?= clang-format
            格式化工具的名字。

第 17-19 行 BIN_DIR  := bin
            APP      := $(BIN_DIR)/ordo
            TEST_BIN := $(BIN_DIR)/ordo_test
            输出路径。$(BIN_DIR) 是变量引用语法。

第 21 行    APP_SRC  := src/main.cpp
            主程序自己的源文件（它含 main 函数，不能进库）。

第 22 行    LIB_SRC  := $(filter-out $(APP_SRC),$(wildcard src/*.cpp src/*/*.cpp src/*/*/*.cpp))
            "库"部分的源文件：把 src 下三层目录里的所有 .cpp 找出来，
            但排除 main.cpp（因为 main 只能有一个）。
            filter-out 是"过滤掉"，wildcard 是"通配符展开"。
            这样以后新增 src/core/task.cpp 会自动被编译，不用改 Makefile。

第 23 行    TEST_SRC := $(wildcard tests/*.cpp)
            测试程序的源文件。

第 24 行    HEADERS  := $(wildcard include/ordo/*.h include/ordo/*/*.h include/ordo/*/*/*.h)
            所有头文件。把它们列进依赖，是为了让"改了 .h 也能触发重新编译"。

第 28 行    .PHONY: all test clean fmt fmt-check help run
            声明这些是"伪目标"：它们不对应真实文件，
            即使目录里恰好有叫 test 的文件，也会照常执行。

第 30 行    all: $(APP)
            默认目标（第一个目标就是默认目标）。make 不带参数时执行这个。

第 32 行    $(APP): $(LIB_SRC) $(APP_SRC) $(HEADERS)
            生成 bin/ordo 的规则：只要有任何源文件或头文件比它新，就重新编译。
            这就是"增量构建"——没改的就不重编译。

第 33 行    	@mkdir -p $(BIN_DIR)
            开头的 @ 表示"执行这条命令但不要把命令本身打印到屏幕"。
            mkdir -p 保证目录存在（已存在也不报错）。

第 34 行    	$(CXX) $(CXXFLAGS) -o $@ $(LIB_SRC) $(APP_SRC) $(LDFLAGS)
            $@ 是 Make 的自动变量，代表"当前目标的名字"，这里是 bin/ordo。
            整行意思：用 g++ 把库源文件和主程序源文件编译链接成一个可执行文件。

第 35 行    	@echo "==> built: $@"
            打印构建完成提示。

第 37-39 行 同样的规则，生成测试程序 bin/ordo_test：
            - 相同的库源文件 LIB_SRC
            - 换成测试源文件 TEST_SRC（里面有 test_main.cpp 提供的 main）

第 41-43 行 test: $(TEST_BIN)
            先确保测试程序已编译，然后直接运行它。
            因为测试程序失败时返回 1，make 会跟着报错，所以"测试挂了 = 构建失败"。

第 45-46 行 run: $(APP)
            编译后直接运行主程序，省得你敲两遍。

第 48-50 行 clean:
            rm -rf $(BIN_DIR) build
            删掉所有编译产物。改完 Makefile 或怀疑编译缓存有问题时用它。

第 52-55 行 fmt:
            用 clang-format 按 .clang-format 的规则就地重排所有源码。
            注意本机可能没装 clang-format，没装的话这条会报"命令不存在"，
            不影响编译和测试。

第 57-59 行 fmt-check:
            --dry-run 只检查不修改，--Werror 把"格式不一致"当成错误，
            适合提交前跑一遍。

第 61-68 行 help:
            打印所有目标的说明（make help）。

【为什么没有 CMake】

  这个决定及其"什么时候该反悔"写在 docs/adr/0001-architecture.md 决策 2。

    IncludeCategories    规定 #include 的排序：先项目头文件，再第三方，最后标准库
  有了它，代码风格不用靠人自觉，跑一遍 make fmt 就统一了。

第四部分  读这份代码需要的 C++ 知识点

这一节把本项目已经用到的语法点单独拎出来，每个都用一句话讲清楚。

  #include <x>        引入标准库头文件，编译器到系统目录找
  #include "x"        引入项目内头文件，编译器先找当前目录，再找 -I 指定的目录
  #pragma once       头文件只被处理一次，防止重复定义
  #define NAME 值     宏定义，编译前做纯文本替换
  #define F(x) ...     带参数的宏

  \ 行尾续行         宏太长时换行用的
  namespace ns { }   命名空间，避免名字冲突
  namespace { }      匿名命名空间，内容只在本文件可见（=C 的 static）
  namespace a::b { } C++17 嵌套命名空间写法
  struct / class     struct 默认成员公开，class 默认私有；本项目的 TestCase 只存数据，用 struct
  int& / const T&    引用：是别名不是拷贝；const& 表示只读，常用于传参
  void (*fn)()       函数指针：指向"无参无返回"的函数
  static 局部变量    只初始化一次，函数返回后仍然存在（本项目用它做全局登记表）
  inline             允许函数/变量定义在头文件中而不违反"一次定义规则"
  constexpr          编译期常量，零运行时开销
  auto               让编译器自动推导类型
  三目 a ? b : c     条件表达式，比 if 短
  范围 for           for (const auto& x : 容器) 依次遍历
  std::string_view   只读字符串视图，不拷贝，适合做参数
  std::ostringstream 把各种类型拼成一个字符串
  std::move          把一个对象"搬"过去，避免深拷贝
  do { } while (0)   宏的标准外壳，保证展开后是一条语句
  __FILE__ __LINE__  编译器内置宏，展开为当前文件名和行号
  %s %d %zu          printf 系列占位符：字符串 / 整数 / size_t
  cerr / cout        cerr 走错误流（stderr），cout 走标准输出（stdout）
  return 0 / 非 0    退出码：0 表示成功，非 0 表示失败

================================================================================
第五部分  一次完整运行发生了什么
================================================================================

把命令和代码串起来看一遍，以后遇到问题就知道该查哪一环。

【场景 A：编译】

  $ mingw32-make

  1. make 读取 Makefile，确定默认目标是 all
  2. all 依赖 bin/ordo，bin/ordo 又依赖 LIB_SRC + APP_SRC + HEADERS
  3. make 比较文件修改时间，发现源码比 exe 新，决定重新编译
  4. 执行 mkdir -p bin
  5. 执行 g++ -std=c++17 ... -o bin/ordo src/main.cpp
     g++ 分四步：预处理（展开 #include 和宏）→ 编译（变汇编）→ 汇编（变机器码）
                  → 链接（把所有 .o 拼成一个 exe）
  6. 生成 bin/ordo.exe，打印 "==> built: bin/ordo"

【场景 B：运行】

  $ ./bin/ordo --version

  1. 操作系统加载 bin/ordo.exe
  2. 进入 main()，argc = 2，argv[0] = 程序路径，argv[1] = "--version"
  3. 循环从 i = 1 开始，arg = "--version"
  4. 命中第 27 行的判断，打印 "ordo 0.1.0"
  5. return 0，操作系统收到退出码 0

【场景 C：测试】

  $ mingw32-make test

  1. make 发现 bin/ordo_test 不存在或过期，先编译它
     编译时链接的是 tests/test_main.cpp + tests/test_version.cpp（含两个 main 中的一个）
  2. 运行 bin/ordo_test.exe
  3. 进程启动时，test_version.cpp 里那个全局 Registrar 对象自动构造
     → 它的构造函数把 (名字, 函数指针) 塞进全局登记表
  4. 进入 test_main.cpp 的 main()，取出登记表
  5. 逐个调用用例函数
  6. 每个 ORDO_CHECK 断言失败就调用 report_failure，计数 +1
  7. 打印汇总，全过返回 0，有失败返回 1
  8. make 看到返回 0，认为成功，结束

理解这三条链路，就理解了"源码 → 可执行文件 → 进程 → 退出码"的全过程。

================================================================================
第六部分  常见问题
================================================================================

Q: 敲 make 提示 make: command not found
A: 本机装的是 MinGW，命令名是 mingw32-make。用 mingw32-make，
   或者给 make 建个别名。

Q: 提示 g++: command not found
A: g++ 不在 PATH 里。本机它在 C:\Users\Jerry\.vscode\mingw64\bin。
   把这个目录加进系统环境变量 PATH，或者在 Makefile 里把 CXX 改成绝对路径。

Q: 运行时中文显示成乱码
A: Windows 控制台默认不是 UTF-8。先执行 chcp 65001 切到 UTF-8 再运行。
   本项目为了避开这个问题，编译提示和程序输出都用英文，中文只出现在
  注释和文档里。

Q: 改了代码，运行结果没变
A: 没重新编译。跑 mingw32-make，或者 mingw32-make clean && mingw32-make。

Q: bin/ 目录里为什么没有东西
A: bin/ 是编译产物，一次都没编译过就是空的。先跑 mingw32-make。

Q: 为什么 data/ 只有一个 .gitkeep
A: 数据文件要等 M1 才有。.gitkeep 只是为了让 git 保留这个空目录。

Q: 为什么程序运行起来什么都不做
A: 当前是 M0 骨架阶段，只有 --version 和 --help 两个参数能用。
   业务功能从 M1 开始实现。

Q: 测试只有一个，是不是没写完
A: 是。M0 阶段只保留一个冒烟测试，用来证明"测试框架本身能跑通"。
   每个里程碑都会增加对应测试。

Q: 为什么不用 CMake / GTest / nlohmann-json
A: 四条架构决策的理由都写在 docs/adr/0001-architecture.md。
   一句话：本机没有 cmake，第三方依赖是长期维护的最大风险。

第七部分  下一步会加什么（M1 顺序建议）
================================================================================

按这个顺序做，每一步做完都能编译、能测，不会卡在半成品状态：

  第 1 步  core/result.h       先写 Result<T> 和 ErrorCode，后面的函数都要用它
  第 2 步  core/types.h        定义 TaskId / Minutes / TimePoint
  第 3 步  core/task.h         定义 Task 结构体 + validate()
  第 4 步  io/csv.h            CSV 解析（先写纯函数，最容易测）
  第 5 步  io/repository.h     ITaskRepository 接口
  第 6 步  io/file_repository.h  CSV 文件实现（临时文件 + 原子替换）
  第 7 步  algo/priority.h     加权打分与排序
  第 8 步  algo/edf.h          最早截止优先排序
  第 9 步  app/task_service.h  把上面几件拼起来：增删改查
  第 10 步 cli/command.h + dispatcher.h + menu.h   命令行入口
  第 11 步 改 src/main.cpp     装配所有对象，删掉 skeleton 那行
  第 12 步 data/tasks.csv + data/config.ini  给一套能跑的样例数据

每写完一个文件，就补一个 tests/test_xxx.cpp，最少 4 个用例，含一个边界。
全部做完整跑一遍 mingw32-make test，绿了再进 M2。
