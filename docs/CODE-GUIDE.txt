--------------------------------------------------------------------------------
1.1  一句话
--------------------------------------------------------------------------------

Ordo 是一个用 C++ 写的命令行小工具：你把"这周要做的任务"录进去，它告诉你
今晚先做哪件、做多久、哪件已经排不下了。

名字来自拉丁语 ordo（次序、编排）。中文名叫"学习任务编排器"。

--------------------------------------------------------------------------------
1.2  它到底解决什么问题（举一个具体例子）
--------------------------------------------------------------------------------

假设今晚 18:30 到 23:00 你有 270 分钟，手上有三件事：

  A. 高数作业     截止明天 08:00   预估 90 分钟   重要度 5
  B. 英语背单词   截止三天后       预估 30 分钟   重要度 3
  C. 实验报告     截止下周         预估 180 分钟  重要度 4

一个"待办清单"只能把这三条列出来，怎么排全靠你自己想。
Ordo 要做的是：

  1. 算紧急度：A 明天就交，最急；C 还早但有 180 分钟，排不下；
  2. 排顺序：A → B → C，并说明为什么；
  3. 装箱：把 270 分钟切成 90 + 30 + 150，C 还剩 30 分钟排不进去；
  4. 报冲突：明确告诉你"C 差 30 分钟，建议今晚少睡半小时或改到明晚"。

第 4 步是关键：排不下不是错误，是必须能被解释的结果。

1.4  五分钟跑起来
--------------------------------------------------------------------------------

打开终端（Git Bash 或 PowerShell 都行），进入项目根目录，依次执行：

  命令 1:  mingw32-make
  会发生:  调用 g++ 编译 src/ 下全部 .cpp，生成 bin/ordo.exe
  成功标志: 屏幕上出现 "==> built: bin/ordo"

  命令 2:  ./bin/ordo --version
  会发生:  运行程序，打印 "ordo 0.2.0"
  说明:    --version 是命令行参数，程序识别到它就直接打印版本然后退出

  命令 3:  ./bin/ordo-gui
  会发生:  打开图形界面（Windows 原生窗口）
  说明:    列表、筛选、排序、增删改、统计都在一个窗口里完成

  命令 4:  ./bin/ordo
  会发生:  进入文本菜单（1 添加 / 2 查看 / 3 完成 / 4 修改 / 5 删除 / 6 统计 / 0 退出）
  说明:    不带参数时进入菜单；带参数则执行一条命令，例如
           ./bin/ordo task list --rank score

  命令 5:  mingw32-make test
  会发生:  编译测试程序，然后运行 41 个测试用例，全部通过
  成功标志: "41 case(s), 0 assertion failure(s)"

  命令 5:  mingw32-make clean
  会发生:  删除 bin/ 目录，把编译产物清干净

为什么要用 mingw32-make 而不是 make？
  本机安装的是 MinGW 工具链，它提供的命令名就叫 mingw32-make，没有 make。
  在 Linux / macOS 上把命令换成 make 就能用，Makefile 本身是通用的。

2.2  五层结构（这是"单元"的概念）
--------------------------------------------------------------------------------

代码不是一个 main 从头写到尾，而是分成五"层"（单元）。箭头表示"谁可以调用谁"：

   ┌────────────────────────────────────────────────────────┐
   │  cli/     命令层    读命令行参数 / 显示菜单 / 打印结果   │
   └───────────────────────────┬────────────────────────────┘
                               │ 只能往下调
   ┌───────────────────────────▼────────────────────────────┐
   │  app/     服务层    串起"取数据 → 算算法 → 存回去"      │
   └───────────┬───────────────────────────────┬────────────┘
               │                               │
   ┌───────────▼──────────────┐    ┌───────────▼────────────┐
   │  algo/   算法层（纯计算） │    │  io/     存储层（读写） │
   │  不碰文件、不碰时间       │    │  只认接口，实现可替换   │
   └──────────────────────────┘    └────────────────────────┘

为什么非要分这么细？三个理由：

  1. 能测试。算法层只接受"输入参数"、只返回"结果"，不读文件也不问系统时间，
     所以可以在没有数据文件的情况下单独测它算得对不对。
  2. 能替换。存储层藏在接口后面，将来从 CSV 换成 JSON，只改一个文件，
     上层一行都不用动。
  3. 能解释。答辩时被问"你的核心算法在哪"，答案是 algo/ 目录，不含糊。

铁律（违反任何一条都算设计错误，不是风格问题）：

  - cli/ 里不许出现 ifstream / ofstream（不许自己读写文件）
  - algo/ 里不许调用系统时钟（当前时间必须由调用方当参数传进来）
  - algo/ 里不许抛异常（失败用返回值表达）
  - io/ 的具体实现只在 src/main.cpp 里创建一次

--------------------------------------------------------------------------------
3.1  include/ordo/version.h    （8 行）
--------------------------------------------------------------------------------

【它是什么】
  版本号的唯一出处。程序里任何地方要用版本号，都包含这个文件，
  而不是到处手写 "0.2.0"。将来改版本只改这一处。

【逐行说明】

第 1 行   #pragma once
          头文件保护。同一个 .h 被多次 #include 时，编译器只处理第一次。
          老写法是 #ifndef/#define/#endif 三行，现在一行就够。

第 3 行   // Ordo 版本宏。与 CHANGELOG.md 保持一致，发布时同步修改。
          // 是单行注释，编译器完全忽略。

第 4 行   #define ORDO_VERSION_MAJOR 0
          定义"主版本号"宏，值是 0。宏是编译期的纯文本替换：
          代码里写 ORDO_VERSION_MAJOR，编译前就被换成 0。

第 5 行   #define ORDO_VERSION_MINOR 1
          次版本号，值是 1。项目做了向下兼容的新功能时 +1。

第 6 行   #define ORDO_VERSION_PATCH 0
          修订号，修 bug 时 +1。

第 8 行   #define ORDO_VERSION_STRING "0.2.0"
          给人看的完整版本字符串。注意值是带双引号的，它是一个字符串字面量。
          有了它，代码里可以写：
              std::cout << "ordo " ORDO_VERSION_STRING;
          两个字符串字面量挨在一起，C++ 会自动拼接成 "ordo 0.2.0"。

【一个坑】
  三个数字宏和这个字符串宏是分开维护的，改版本时必须一起改，否则会对不上。
  M1 可以考虑用一个宏自动拼出字符串，目前这样写更直白，适合新手阅读。

--------------------------------------------------------------------------------
3.2  src/main.cpp    （M1 重写，约 200 行）
--------------------------------------------------------------------------------

【它是什么】
  程序入口，也是唯一的依赖装配点。M1 重写后它做四件事：

  1. 把 Windows 控制台切到 UTF-8（enable_utf8_console）；
  2. 取命令行参数——Windows 上从 GetCommandLineW 重新转成 UTF-8，
     避免 CRT 按 ANSI 代码页解码导致中文参数乱码（utf8_arguments）；
  3. 解析全局选项与通用 "--flag value"（parse_cli）；
  4. 装配 Repository → AppContext → Dispatcher → 菜单，然后运行。

【结构】

  enable_utf8_console()    仅 Windows：SetConsoleOutputCP/SetConsoleCP(CP_UTF8)
  utf8_arguments()         Windows：CommandLineToArgvW + WideCharToMultiByte；
                           其它平台回退到 main 的 argv
  all_digits / looks_like_date / looks_like_time
                           让 `--due 2026-10-30 23:59` 不写引号也能合并成一个值
  struct Cli               解析结果：Args + 数据文件路径 + help/version 标志
  parse_cli()              手写参数解析：--name=value、--name value、位置参数
  main()                   try/catch 包住全部业务；异常只在这里转成退出码

【关键点】

  - CsvTaskRepository 只在 main 里构造一次，向下以引用传递
    （OUTLINE §7.1 硬规则 3）。
  - 时钟以 lambda 注入 AppContext；命令层调用 ctx.now()，
    算法层仍然只接受 now 参数，不自己问系统时间。
  - 不带命令时进入 Menu，带命令时交给 Dispatcher；
    两者共用同一套 Command，不维护两份逻辑。
  - 退出码：0 成功 / 1 业务失败 / 2 用法错误。

--------------------------------------------------------------------------------
3.3  tests/test_framework.h    （65 行）
--------------------------------------------------------------------------------

【它是什么】
  自研的极简测试框架，约 65 行，零第三方依赖。
  它让你可以这样写测试：

      ORDO_TEST(加法应该正确) {
          ORDO_CHECK_EQ(1 + 1, 2);
      }

  然后 make test 会自动找到这个用例并运行它。

【它解决的核心问题】
  怎么让"定义了测试用例"这件事自动被登记，不用手动一个个调用？
  答案是：利用 C++ 的"静态对象在 main 之前构造"这一特性。

【逐行说明】

第 1 行     #pragma once
            头文件保护，同上。

第 3-7 行   // 使用说明注释

第 9-13 行  #include 五个标准库头文件
            <cstdio>   提供 std::fprintf（格式化输出到 stderr）
            <sstream>  提供 std::ostringstream（把内容拼成字符串）
            <string>   提供 std::string
            <utility>  提供 std::move（把字符串"搬"进容器，避免拷贝）
            <vector>   提供 std::vector（动态数组）

第 15 行    namespace ordo::test {
            C++17 的嵌套命名空间写法，等价于 namespace ordo { namespace test { 。
            测试相关的东西放在 ordo::test 下，和业务代码隔开。

第 17-20 行 struct TestCase {
                std::string name;   // 用例名字，用于打印
                void (*fn)();       // 函数指针：指向"没有参数、没有返回值"的函数
            };
            一个 TestCase 就是"名字 + 一段可执行的代码"。

第 22-25 行 inline std::vector<TestCase>& registry() {
                static std::vector<TestCase> cases;
                return cases;
            }
            返回"用例登记表"。两个关键点：
              1. static 局部变量只在第一次执行到这里时构造一次，
                 之后一直存在，函数返回时也不会销毁。这是全局唯一的表。
              2. inline 允许这个函数在多个 .cpp 里各有一份定义而不冲突
                 （C++17 起 inline 变量/函数可以放在头文件里）。
            返回引用 &，所以外面拿到的是同一张表，不是副本。

第 27-30 行 inline int& failure_count() {
                static int failures = 0;
                return failures;
            }
            同上，返回"失败计数器"的引用。所有用例共享这一个计数器。

第 32-34 行 struct Registrar {
                Registrar(std::string name, void (*fn)()) {
                    registry().push_back({std::move(name), fn});
                }
            };
            登记员。构造函数一被调用，就把 (名字, 函数) 塞进登记表。
            它的用法在第 45 行的宏里——定义一个全局 Registrar 对象，
            程序启动时它的构造函数自动执行，用例就登记好了。
            这就是"零配置发现测试"的原理。

第 36-39 行 inline void report_failure(const char* file, int line,
                                            const std::string& what) {
                ++failure_count();                       // 失败数 +1
                std::fprintf(stderr, "  FAIL  %s:%d\n        %s\n",
                             file, line, what.c_str());
            }
            fprintf 是 C 语言的格式化输出：%s 占位字符串，%d 占位整数。
            what.c_str() 把 std::string 转成 C 风格字符串，因为 %s 要 char*。
            const std::string& 用引用传参，避免整个字符串被拷贝一遍。

第 41 行    }
            命名空间结束。

第 43-46 行 #define ORDO_TEST(case_name)                       \
                static void case_name();                       \
                static ::ordo::test::Registrar case_name##_registrar{#case_name, case_name}; \
                static void case_name()

            宏，把一行声明展开成三行：
              第 1 行：先声明一个函数（正式定义在用户写的大括号里）
              第 2 行：定义一个全局登记对象，名字 = 用例名 + "_registrar"
                       ## 是宏里的"拼接运算符"，case_name##_registrar
                       在 case_name 为 foo 时会变成 foo_registrar
                       ::ordo 前面的双冒号表示"从全局命名空间开始找"
              第 3 行：以 static void case_name() 开头，后面紧跟用户写的 { ... }

            所以用户写：
                ORDO_TEST(foo) { ORDO_CHECK(true); }
            展开后就是"函数声明 + 登记对象 + 函数定义"三合一。
            行尾的 \ 表示"这一行还没结束，下一行接着"。右边对齐的反斜杠只是好看。

第 48-53 行 #define ORDO_CHECK(cond) ...
                do {
                    if (!(cond)) {
                        ::ordo::test::report_failure(__FILE__, __LINE__, "assert: " #cond);
                    }
                } while (0)

            - __FILE__ / __LINE__ 是编译器内置宏，自动展开成当前文件名和行号。
            - #cond 是宏里的"字符串化运算符"，把参数原样变成字符串。
              所以失败时会打印 "assert: 1 + 1 == 3" 这样的原文。
            - 外面套 do { } while (0) 的原因：宏展开后如果不套循环，
              在 if 后面直接跟这个宏时会出现悬空 else 问题；
              包成一条语句就永远不会出错。这是 C/C++ 宏的标准防御写法。

第 55-65 行 #define ORDO_CHECK_EQ(actual, expected) ...
                do {
                    const auto& a_ = (actual);     // auto 自动推导类型
                    const auto& e_ = (expected);   // const& 避免拷贝
                    if (!(a_ == e_)) {
                        std::ostringstream os_;
                        os_ << #actual " == " #expected << "\n        actual  : " << a_
                            << "\n        expected: " << e_;
                        report_failure(__FILE__, __LINE__, os_.str());
                    }
                } while (0)

            比较两个值，不等就把"实际值"和"期望值"都打印出来，
            省得你再去猜到底差在哪。os_.str() 把拼好的内容取出成 std::string。
            a_ / e_ 加了尾随下划线，是为了避免和你传进来的变量重名。

【小结：这个 65 行文件教了你什么】
  - static 局部变量 = 函数内隐藏的全局变量
  - inline 让函数能安全地写在头文件里
  - 构造函数可以在 main 之前执行（全局对象初始化）
  - 宏里的 # 和 ## 分别做什么
  - do { } while (0) 为什么是宏的标准外壳

--------------------------------------------------------------------------------
3.4  tests/test_main.cpp    （21 行）
--------------------------------------------------------------------------------

【它是什么】
  测试程序的入口。make test 编译出来的 bin/ordo_test.exe 从这里开始跑。

【逐行说明】

第 1 行     // 注释

第 3 行     #include <cstdio>
            为了用 std::printf。

第 5 行     #include "test_framework.h"
            双引号：找同目录下的文件（tests/ 目录）。

            记下跑这个用例之前的失败数。

第 13 行    c.fn();

            三目运算符 a ? b : c：passed 为真取 "ok  "，否则取 "FAIL"。

第 16 行    }

            汇总总失败数。

第 19 行    std::printf("\n%zu case(s), %d assertion failure(s)\n",

3.6  Makefile    （68 行）
--------------------------------------------------------------------------------

【它是什么】
  构建脚本。一行命令就能完成"编译全部源文件 → 生成可执行文件"。
  它同时是测试、清理、格式化的入口。

【整体结构】
  变量定义（1-24 行）→ 目标定义（26-68 行）
  Makefile 的语法是"目标: 依赖，然后换行 + TAB + 执行命令"。
  注意：命令前面必须是 TAB，不能是空格，这是 Make 最容易踩的坑。

【逐段说明】

第 1-4 行   # 注释：文件用途和用法

第 6-10 行  # Windows 下 mingw32-make 默认用 cmd.exe 执行命令，
            # mkdir -p / rm -rf 会失败。
            # 显式指定 POSIX shell（Git for Windows 自带 sh.exe）。
            ifeq ($(OS),Windows_NT)
            SHELL    := sh
            endif

            这一段是为了跨平台：Windows 的 cmd 不认识 mkdir -p 和 rm -rf，
            所以强制改用 sh 来执行命令。
            := 是"立即展开赋值"，?= 是"只在未定义时赋值"。

第 12 行    CXX      ?= g++
            编译器名字。如果环境里已有 CXX 变量，就用环境的，否则用 g++。

第 13 行    CXXFLAGS ?= -std=c++17 -Wall -Wextra -Wpedantic -Wshadow -Iinclude -O2 -g
            编译选项，逐个解释：
              -std=c++17   使用 C++17 标准
              -Wall        打开常见警告
              -Wextra     打开更多警告
              -Wpedantic  严格按标准检查
              -Wshadow    变量遮蔽同名变量时警告
              -Iinclude   头文件的搜索目录（所以能写 #include "ordo/version.h"）
              -O2         二级优化，让程序跑得快
              -g          保留调试信息，方便 gdb 调试

第 14 行    LDFLAGS  ?=
            链接选项，目前为空。

第 15 行    FORMAT   ?= clang-format
            格式化工具的名字。

第 17-19 行 BIN_DIR  := bin
            APP      := $(BIN_DIR)/ordo
            TEST_BIN := $(BIN_DIR)/ordo_test
            输出路径。$(BIN_DIR) 是变量引用语法。

第 21 行    APP_SRC  := src/main.cpp
            主程序自己的源文件（它含 main 函数，不能进库）。

第 22 行    LIB_SRC  := $(filter-out $(APP_SRC),$(wildcard src/*.cpp src/*/*.cpp src/*/*/*.cpp))
            "库"部分的源文件：把 src 下三层目录里的所有 .cpp 找出来，
            但排除 main.cpp（因为 main 只能有一个）。
            filter-out 是"过滤掉"，wildcard 是"通配符展开"。
            这样以后新增 src/core/task.cpp 会自动被编译，不用改 Makefile。

第 23 行    TEST_SRC := $(wildcard tests/*.cpp)
            测试程序的源文件。

第 24 行    HEADERS  := $(wildcard include/ordo/*.h include/ordo/*/*.h include/ordo/*/*/*.h)
            所有头文件。把它们列进依赖，是为了让"改了 .h 也能触发重新编译"。

第 28 行    .PHONY: all test clean fmt fmt-check help run
            声明这些是"伪目标"：它们不对应真实文件，
            即使目录里恰好有叫 test 的文件，也会照常执行。

第 30 行    all: $(APP)
            默认目标（第一个目标就是默认目标）。make 不带参数时执行这个。

第 32 行    $(APP): $(LIB_SRC) $(APP_SRC) $(HEADERS)
            生成 bin/ordo 的规则：只要有任何源文件或头文件比它新，就重新编译。
            这就是"增量构建"——没改的就不重编译。

第 33 行    	@mkdir -p $(BIN_DIR)
            开头的 @ 表示"执行这条命令但不要把命令本身打印到屏幕"。
            mkdir -p 保证目录存在（已存在也不报错）。

第 34 行    	$(CXX) $(CXXFLAGS) -o $@ $(LIB_SRC) $(APP_SRC) $(LDFLAGS)
            $@ 是 Make 的自动变量，代表"当前目标的名字"，这里是 bin/ordo。
            整行意思：用 g++ 把库源文件和主程序源文件编译链接成一个可执行文件。

第 35 行    	@echo "==> built: $@"
            打印构建完成提示。

第 37-39 行 同样的规则，生成测试程序 bin/ordo_test：
            - 相同的库源文件 LIB_SRC
            - 换成测试源文件 TEST_SRC（里面有 test_main.cpp 提供的 main）

第 41-43 行 test: $(TEST_BIN)
            先确保测试程序已编译，然后直接运行它。
            因为测试程序失败时返回 1，make 会跟着报错，所以"测试挂了 = 构建失败"。

第 45-46 行 run: $(APP)
            编译后直接运行主程序，省得你敲两遍。

第 48-50 行 clean:
            rm -rf $(BIN_DIR) build
            删掉所有编译产物。改完 Makefile 或怀疑编译缓存有问题时用它。

第 52-55 行 fmt:
            用 clang-format 按 .clang-format 的规则就地重排所有源码。
            注意本机可能没装 clang-format，没装的话这条会报"命令不存在"，
            不影响编译和测试。

第 57-59 行 fmt-check:
            --dry-run 只检查不修改，--Werror 把"格式不一致"当成错误，
            适合提交前跑一遍。

第 61-68 行 help:
            打印所有目标的说明（make help）。

【为什么没有 CMake】
  本机没装 cmake，而 g++ + mingw32-make 已经够用。
  这个决定及其"什么时候该反悔"写在 docs/adr/0001-architecture.md 决策 2。

3.7  四个配置文件
--------------------------------------------------------------------------------

.gitignore（约 30 行）
  告诉 git 哪些文件不要提交。三类：
    构建产物：bin/ build/ *.exe *.o ——这些能重新生成，不该进仓库
    临时文件：*.tmp *.bak *.log
    编辑器文件：.vscode/ .idea/ *.swp
  特别说明：!data/log.csv 这一行是"例外规则"，
  表示"虽然 *.log 都忽略，但 data/log.csv 要保留"（它是程序数据不是日志）。

.gitattributes（约 13 行）
  统一换行符。第 1 行 * text=auto eol=lf 的意思是：
  所有文本文件在仓库里一律用 LF（Unix 换行）。
  这样你在 Windows 上编辑、在 Linux 上编译，不会出现"整个文件都变了"的假改动。
  后面单独列出 .pdf/.png/.exe 为 binary，告诉 git 不要对它们做文本处理。

.editorconfig（约 24 行）
  编辑器共用配置。它不强制任何人，但支持它的编辑器（VS Code、CLion 等）
  读到后会自动设置：UTF-8 编码、LF 换行、文件末尾留空行、
  C++ 用 4 空格缩进、Makefile 用 TAB 缩进（Makefile 必须用 TAB！）。

.clang-format（约 30 行）
  clang-format 的规则文件。关键几项：
    BasedOnStyle: LLVM   以 LLVM 风格为底
    IndentWidth: 4       4 空格缩进
    ColumnLimit: 100     一行最多 100 字符
    BreakBeforeBraces: Attach   大括号跟在语句同一行
    IncludeCategories    规定 #include 的排序：先项目头文件，再第三方，最后标准库
  有了它，代码风格不用靠人自觉，跑一遍 make fmt 就统一了。

第四部分  读这份代码需要的 C++ 知识点
================================================================================

这一节把本项目已经用到的语法点单独拎出来，每个都用一句话讲清楚。

  #include <x>        引入标准库头文件，编译器到系统目录找
  #include "x"        引入项目内头文件，编译器先找当前目录，再找 -I 指定的目录
  #pragma once       头文件只被处理一次，防止重复定义
  #define NAME 值     宏定义，编译前做纯文本替换
  #define F(x) ...     带参数的宏
  # 和 ##            宏里：# 把参数变字符串，## 把两段名字粘成一个
  \ 行尾续行         宏太长时换行用的
  namespace ns { }   命名空间，避免名字冲突
  namespace { }      匿名命名空间，内容只在本文件可见（=C 的 static）
  namespace a::b { } C++17 嵌套命名空间写法
  struct / class     struct 默认成员公开，class 默认私有；本项目的 TestCase 只存数据，用 struct
  int& / const T&    引用：是别名不是拷贝；const& 表示只读，常用于传参
  void (*fn)()       函数指针：指向"无参无返回"的函数
  static 局部变量    只初始化一次，函数返回后仍然存在（本项目用它做全局登记表）
  inline             允许函数/变量定义在头文件中而不违反"一次定义规则"
  constexpr          编译期常量，零运行时开销
  auto               让编译器自动推导类型
  三目 a ? b : c     条件表达式，比 if 短
  范围 for           for (const auto& x : 容器) 依次遍历
  std::string_view   只读字符串视图，不拷贝，适合做参数
  std::ostringstream 把各种类型拼成一个字符串
  std::move          把一个对象"搬"过去，避免深拷贝
  do { } while (0)   宏的标准外壳，保证展开后是一条语句
  __FILE__ __LINE__  编译器内置宏，展开为当前文件名和行号
  %s %d %zu          printf 系列占位符：字符串 / 整数 / size_t
  cerr / cout        cerr 走错误流（stderr），cout 走标准输出（stdout）
  return 0 / 非 0    退出码：0 表示成功，非 0 表示失败

================================================================================
第五部分  一次完整运行发生了什么
================================================================================

把命令和代码串起来看一遍，以后遇到问题就知道该查哪一环。

【场景 A：编译】

  $ mingw32-make

  1. make 读取 Makefile，确定默认目标是 all
  2. all 依赖 bin/ordo，bin/ordo 又依赖 LIB_SRC + APP_SRC + HEADERS
  3. make 比较文件修改时间，发现源码比 exe 新，决定重新编译
  4. 执行 mkdir -p bin
  5. 执行 g++ -std=c++17 ... -o bin/ordo src/main.cpp
     g++ 分四步：预处理（展开 #include 和宏）→ 编译（变汇编）→ 汇编（变机器码）
                  → 链接（把所有 .o 拼成一个 exe）
  6. 生成 bin/ordo.exe，打印 "==> built: bin/ordo"

【场景 B：运行】

  $ ./bin/ordo --version

  1. 操作系统加载 bin/ordo.exe
  2. 进入 main()，argc = 2，argv[0] = 程序路径，argv[1] = "--version"
  3. 循环从 i = 1 开始，arg = "--version"
  4. 命中第 27 行的判断，打印 "ordo 0.2.0"
  5. return 0，操作系统收到退出码 0

【场景 C：测试】

  $ mingw32-make test

  1. make 发现 bin/ordo_test 不存在或过期，先编译它
     编译时链接的是 tests/test_main.cpp + tests/test_version.cpp（含两个 main 中的一个）
  2. 运行 bin/ordo_test.exe
  3. 进程启动时，test_version.cpp 里那个全局 Registrar 对象自动构造
     → 它的构造函数把 (名字, 函数指针) 塞进全局登记表
  4. 进入 test_main.cpp 的 main()，取出登记表
  5. 逐个调用用例函数
  6. 每个 ORDO_CHECK 断言失败就调用 report_failure，计数 +1
  7. 打印汇总，全过返回 0，有失败返回 1
  8. make 看到返回 0，认为成功，结束

理解这三条链路，就理解了"源码 → 可执行文件 → 进程 → 退出码"的全过程。

================================================================================
第六部分  常见问题
================================================================================

Q: 敲 make 提示 make: command not found
A: 本机装的是 MinGW，命令名是 mingw32-make。用 mingw32-make，
   或者给 make 建个别名。

Q: 提示 g++: command not found
A: g++ 不在 PATH 里。本机它在 C:\Users\Jerry\.vscode\mingw64\bin。
   把这个目录加进系统环境变量 PATH，或者在 Makefile 里把 CXX 改成绝对路径。

Q: 运行时中文显示成乱码
A: Windows 控制台默认不是 UTF-8。先执行 chcp 65001 切到 UTF-8 再运行。
   本项目为了避开这个问题，编译提示和程序输出都用英文，中文只出现在
  注释和文档里。

Q: 改了代码，运行结果没变
A: 没重新编译。跑 mingw32-make，或者 mingw32-make clean && mingw32-make。

Q: bin/ 目录里为什么没有东西
A: bin/ 是编译产物，一次都没编译过就是空的。先跑 mingw32-make。

Q: 为什么 data/ 只有一个 .gitkeep
A: 数据文件要等 M1 才有。.gitkeep 只是为了让 git 保留这个空目录。

Q: 为什么程序运行起来什么都不做
A: 当前是 M0 骨架阶段，只有 --version 和 --help 两个参数能用。
   业务功能从 M1 开始实现。

Q: 测试只有一个，是不是没写完
A: M0 阶段只保留一个冒烟测试，用来证明"测试框架本身能跑通"。
   M1 已扩展到 41 个用例（core / CSV / 仓库往返 / 排序 / 服务）。
   每个里程碑都只增加对应层次的测试，不跨阶段预写。

Q: 为什么不用 CMake / GTest / nlohmann-json
A: 四条架构决策的理由都写在 docs/adr/0001-architecture.md。

--------------------------------------------------------------------------------
8.1  core/：纯数据与基础设施
--------------------------------------------------------------------------------

core/result.h + result.cpp
  【职责】全项目统一的返回类型。
  【内容】
    - ErrorCode：Ok / NotFound / Duplicate / InvalidFormat / InvalidValue /
      EmptyInput / IoError / Corrupted。
    - Status：code + 面向用户的中文 message，ok() 判断成功。
    - Result<T>：内部是 std::optional<T> + Status。成功必有值，失败必有错误码。
      提供 ok() / fail() / has_value() / value() / status()。
    - error_code_name()：给日志和测试用的稳定英文名，不是给用户看的。
  【关键点】value() 只在 has_value() 为真时调用；内部用 assert 兜住误用。
  【为什么】空数据、格式错、重复 id、文件不存在都是可预期的业务分支，
    用返回值强迫调用方处理；异常只留给 std::bad_alloc 这类真异常，
    在 main() 统一捕获。

core/types.h + types.cpp
  【职责】类型别名与时间/文本工具。
  【内容】
    - TaskId = uint64_t；Minutes = int32_t；Clock / TimePoint。
    - parse_datetime("YYYY-MM-DD HH:MM" 或 "YYYY-MM-DD")：
      只给日期时按当天 23:59；用 mktime 后再逐字段回读，
      这样 2026-02-30 这类会被 mktime 悄悄归一化的日期会被拒绝。
    - format_datetime / format_date：固定格式，不受系统区域设置影响。
    - minutes_between / add_minutes：算法层计时只用这两个函数。
    - trim：去掉首尾空格、制表符、回车、换行，返回 string_view。
  【关键点】内部用 TimePoint，只在输入输出边界转本地时间字符串（OUTLINE §8.3）。

core/task.h + task.cpp
  【职责】Task 实体与不变量校验。
  【内容】
    - 字段：id、title、course、importance(1..5)、estimate(分钟)、deadline、
      state、review_stage、last_review（仅内存，M3 用）。
    - validate()：id>0、标题非空、标题/课程不含换行、重要度 1..5、
      预估非负、截止时间非空；失败返回具体错误码，不做"自动修复"。
    - to_string / parse_task_state：CSV 与 CLI 共用的枚举文本。
    - is_open：todo 或 doing。
    - filter_by_state：按状态过滤，服务层直接用。
  【为什么】Task 只存事实；紧急度、分数这些派生量每次现算，避免过期。

8.2  io/：持久化
--------------------------------------------------------------------------------

io/repository.h
  【职责】C4 存储接口，只有五个纯虚函数：
    load_all / save_all / find / upsert / erase。
  【关键点】上层只认这个接口，换 JSON 或内存实现时不用动服务层。

io/csv.h + csv.cpp
  【职责】CSV 行级纯函数，不碰文件、不认识 Task。
  【内容】
    - parse_line：一个小状态机，处理引号内的逗号、"" 转义、空字段；
      引号未闭合返回 InvalidFormat。
    - quote_field / join_fields：只在字段含 , " 换行时加引号。
    - strip_bom：剥掉 Excel 可能写入的 UTF-8 BOM。
  【测试】tests/test_csv.cpp 覆盖逗号、引号、空字段、往返、BOM。

io/file_repository.h + file_repository.cpp
  【职责】ITaskRepository 的 CSV 文件实现。
  【读流程】
    文件不存在 → 空表；逐行读 → 剥 BOM/CRLF → 跳过空行 →
    校验表头 → 字段数必须为 8 → 逐字段解析 → Task::validate →
    重复 id 检查。
  【写流程】
    先逐条 validate → 创建父目录 → 写 tasks.csv.tmp →
    flush + close 检查 → rename 原子替换（失败时先删目标再改名）。
  【错误码】
    结构问题 → Corrupted；值格式 → InvalidFormat；越界 → InvalidValue；
    id 重复 → Duplicate；读写失败 → IoError。
  【为什么整表拒绝】§9.4：宁可明确报错，也不静默丢行，
    否则用户会以为数据还在。

--------------------------------------------------------------------------------
8.3  algo/：纯函数算法
--------------------------------------------------------------------------------

algo/priority.h + priority.cpp
  【职责】加权打分与排序。
  【公式】score = 100 × (0.5×重要度 + 0.3×紧急度 + 0.2×短任务奖励)
    - 重要度：(importance-1)/4，落在 0..1。
    - 紧急度：1/(1+剩余分钟/每日容量)；已超期时进入 (1,2]，
      保证排在所有未超期任务之前。
    - 短任务奖励：1/(1+预估分钟/每日容量)。
  【排序】分数降序 → 截止时间升序 → id 升序，结果确定、可复现。
  【关键点】ScoreFn 是函数指针，默认 score_weighted；以后可换模型，
    服务层只改传参。

algo/edf.h + edf.cpp
  【职责】最早截止优先。
  【排序】截止时间升序 → 重要度降序 → id 升序。
  【关键点】now 参数保留是为了与其它策略同形；EDF 本身不需要 now。

8.4  app/：应用服务
--------------------------------------------------------------------------------

app/context.h
  【职责】命令层能拿到的全部外部依赖：repo 引用、输出流、输入流、时钟。
  【关键点】时钟是 std::function<TimePoint()>，测试时可注入固定时间。

app/task_service.h + task_service.cpp
  【职责】任务增删改查、排序入口、统计。
  【内容】
    - add：先读全表；id 为 0 时取 max(id)+1，非 0 时重复即返回 Duplicate；
      校验后追加并整表保存。
    - update：patch.id 必须等于目标 id；找不到返回 NotFound；
      校验通过才替换并保存。
    - list(state)：按状态过滤。
    - list_ranked(state, mode, now)：过滤 → 调 rank_by_score/rank_by_edf →
      按 id 映射回完整 Task 返回。命令层因此不需要知道 TaskId → Task 的映射。
    - stats(now)：各状态计数、超期数、未完成/已完成预估总时长。
  【为什么】服务层是唯一同时知道"数据从哪来"和"算法怎么用"的地方。

cli/command.h + command.cpp
  【职责】C1 命令层基类。

    - task.list 默认 --state open、--rank none；--rank score/edf 调服务排序。
    - task.edit 只改显式给出的字段；一个字段都没给时报用法错误。
    - 所有输出走 ctx.out，不直接写 std::cout，便于集成测试替换流。

8.7  一条命令的完整调用链
--------------------------------------------------------------------------------

以 ./bin/ordo task list --rank score 为例：

  main
   └─ parse_cli：positional = [task, list]，flags = {rank: score}
   └─ Dispatcher::run：解析出 task.list，消费前两个 token
       └─ TaskListCommand::execute
           └─ TaskService::list_ranked(nullopt, Score, ctx.now())      [C2]
               ├─ repo.load_all()                                      [C4]
               └─ rank_by_score(tasks, score_weighted, ctx)            [C3]
           └─ 遍历结果，按列打印到 ctx.out

命令层没有出现任何文件读写，算法层没有读时钟，存储层只被服务层调用——
这就是四层架构要守住的全部内容。

9.1  为什么要多出 ui/ 这一层

  需求是"先做最基础的界面，保留接口，后期可以加套外部 GUI"。
  如果把"读取控件文字、拼 Task、调服务、刷新列表"直接写在 Win32 窗口过程里，
  将来换成 Qt 或网页就要重写一遍所有表单规则。

  所以拆成两份：

    ui/AppModel    知道"用户填了哪些字段、怎么变成 Task、列表要展示什么"
    gui/           知道"按钮在哪、列表怎么画、消息怎么收"

  gui/ 只调用 AppModel，不碰 CSV；AppModel 只出现 std::string 与 Result，
  不出现 HWND 或 wchar_t。外部 GUI 直接复用 AppModel 即可。

  依赖方向：

    gui/ ──▶ ui/ ──▶ app/ ──▶ { algo/, io/ }
    cli/ ──────────▶ app/

9.2  include/ordo/ui/app_model.h + src/ui/app_model.cpp

  【职责】GUI 无关的界面模型。
  【数据结构】
    ListQuery  查询条件：状态过滤、是否只看未完成、排序方式
    TaskRow    列表一行：id、标题、课程、重要度、预估、截止文本、状态
    TaskForm   表单原始输入：title/course/importance/estimate/deadline 全是字符串
  【方法】

  【关键点】表单解析放在这里，Win32 对话框只负责把控件文字取出来塞进 TaskForm。

--------------------------------------------------------------------------------
10.1  一句话
--------------------------------------------------------------------------------

M1 只会"排顺序"，M2 开始"排时间"：把未完成任务塞进每天的作息窗口，
排不下的写进 warnings，并把"活动"这种不能挪的任务当作固定占位。

M2 还引入了一个模型级改动：任务有类型（课程作业 / 自主学习 / 活动 /
复习考试 / 其他），类型同时影响打分与装箱方式。设计依据是
docs/adr/0003-planning.md。

--------------------------------------------------------------------------------
10.2  任务类型与数据格式
--------------------------------------------------------------------------------

include/ordo/core/task.h

  enum class TaskKind { CourseWork, SelfStudy, Activity, Review, Other };

  Task 新增两个字段：
    TaskKind kind{TaskKind::Other};        // 业务类型
    std::optional<TimePoint> fixed_start;  // 仅 Activity

不变量（src/core/task.cpp 的 Task::validate）：

  - Activity 必须 fixed_start；estimate > 0；deadline >= fixed_start + estimate；
  - 非 Activity 的 fixed_start 必须为空。

CSV 变化（data/tasks.csv）：

  旧：id,title,course,importance,estimate,deadline,state,review_stage
  新：... ,kind,fixed_start

  读取时两种表头都接受；旧表头按 kind=other、fixed_start 空处理。
  保存时统一写新表头，所以旧文件在第一次写入时自动迁移。
  这条兼容逻辑在 src/io/file_repository.cpp 的 load_all / save_all。

--------------------------------------------------------------------------------
10.3  core/slot.h + core/schedule.h
--------------------------------------------------------------------------------

include/ordo/core/slot.h

  FreeSlot { begin, end }   一段可用时间
  Block    { task, begin, end }  一个已排入的时间块

  两者都是半开区间 [begin, end)：19:00 结束的块和 19:00 开始的块不重叠。

  关键函数：
    overlaps(a_begin, a_end, b_begin, b_end)
    intersect(left, right)
    subtract(slots, occupied)   从可用时段里扣掉一个占用区间

  为什么单独做 subtract：活动占位、休息间隔、冲突检测都要"从一段区间里
  挖掉另一段"，写成纯函数后可以在没有任务、没有文件的情况下测试。

include/ordo/core/schedule.h

  Warning { task, reason }   一条解释性告警
  Plan    { blocks, warnings, total_assigned, total_free }

  add_warning / sum_minutes / sort_blocks 都是小工具。
  Plan 里必须有 warnings：排不上不是错误，是正常业务结果。

10.4  io/config.h：读 config.ini
--------------------------------------------------------------------------------

include/ordo/io/config.h

  struct ScheduleConfig {
      Minutes weekday_start{18*60+30};
      Minutes weekday_end{23*60};
      Minutes weekend_start{9*60};
      Minutes weekend_end{22*60};
      Minutes break_minutes{10};
      Minutes default_estimate{60};

      Minutes min_block{15};

  Result<ScheduleConfig> load_config(path);

规则：
  - 文件不存在 → 返回默认值（和 tasks.csv 的首次运行语义一致）；
  - 已知键值非法 → 返回 InvalidFormat，消息带行号；
  - 未知键忽略，便于以后追加配置；
  - 时间写成 HH:MM，解析成"零点起的分钟数"；
  - 读的时候容忍 UTF-8 BOM 与 CRLF。

main.cpp 与 main_gui.cpp 是装配点：它们读配置，再注入 AppContext / AppModel。
algo/ 与 ui/ 不碰文件。

--------------------------------------------------------------------------------
10.5  algo/packer.h + algo/conflict.h
--------------------------------------------------------------------------------

pack 的输入：
  tasks   已经按优先级排好序（score 或 EDF 的输出）
  slots   空闲时段
  policy  allow_split / min_block / gap
  now     当前时刻（由调用方传入，算法不取时钟）

pack 的两轮：

  第一轮：活动
    - 按 fixed_start 生成 [start, start+estimate)；
    - 已经结束的活动 → warning，跳过；
    - 已经开始但没结束 → 从 now 占位，warning 提醒；
    - 从空闲时段里 subtract 掉，保证别的任务不会排进来。

  第二轮：普通任务
    - 一个任务从最早的空闲时段开始填；
    - 能一次装下就整块安排（短任务不受 min_block 限制）；
    - 装不下且允许拆分 → 拿走整段可用时间，块后加 gap；
    - 不允许拆分 → 只接受能一次装下的连续时段；
    - 块结束不得晚于 deadline；
    - 已超期任务忽略截止约束、排最早时段，并给"已超期"告警；
    - 最后还有剩余 → warning 说明差多少分钟。

detect_conflicts：
  把块按开始时间排序，做扫描；两个块重叠时给双方各一条警告。
  半开区间下，19:00 结束与 19:00 开始不算重叠。

--------------------------------------------------------------------------------
10.6  app/plan_service.h
--------------------------------------------------------------------------------

PlanService(repo, config)

  plan_today(now, rank)  → 1 天窗口，所有未完成任务参与，填满今天的空闲时间
  plan_week(now, rank)   → 滚动 7 天，只排截止落在窗口内的任务（含已超期）

内部流程：

  1. repo.load_all()
  2. 过滤：只留 todo/doing；活动按 fixed_start 是否落在窗口内过滤；
     本周计划再按 deadline <= 窗口结束过滤；
  3. 排序：rank_by_score 或 rank_by_edf；
  4. build_free_slots：按工作日/周末作息逐日生成，今天从 max(now, 开始) 算；
  5. pack + detect_conflicts；
  6. 汇总 total_free / total_assigned。

注意窗口语义：
  今日计划回答"今天还能做什么"，所以不按截止过滤；
  本周计划回答"本周要交的活怎么排"，所以只排本周到期的任务，
  避免把下个月的作业排进来。
